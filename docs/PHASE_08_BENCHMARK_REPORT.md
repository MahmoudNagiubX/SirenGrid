# PHASE 08 BENCHMARK REPORT

## Status

This is the reproducible Phase 08 benchmark for the backend and deterministic
local simulation controls. It is a measurement artifact, not a production
service-level evaluation or a claim about Cairo incident frequency.

The functional benchmark contains exactly 36 scenarios: the 15 executable
Master Plan cases T01-T15 and 21 distinct cross-cutting cases. Each engine ran
once per scenario from the same deterministic inputs. The performance subset
contains 10 scenarios, one excluded warm-up, and three isolated measured
repetitions per engine (30 retained timing samples per engine).

The official run was generated by commit
`dcc27904a32631426cf19fcadf5e4db556ad1c52`. The final cache-integrity
regression added after that run is test/documentation-only and does not alter
the benchmark decision logic.

## Methodology and fairness

Both engines received the same incident facts, resource overrides, graph,
fixed traffic fixture or fallback state, hospital registry, simulated
hospital state, real-derived population zones, event order, and seed.
Traffic was never refreshed during a comparison. Fixed traffic fixtures are
replay inputs, not current `REAL_LIVE` traffic.

The baseline is the approved simple greedy policy: process the most
constrained cohort first, then choose the lowest route ETA, route distance,
and resource ID without backtracking or coverage-aware selection. Baseline
coverage is measured after selection using the production
`JOINT_ALL_REQUIRED_COHORTS_V1` engine. Baseline hospital selection uses the
same hard feasibility filters and chooses the lowest route ETA, distance, and
hospital ID; it does not use the SirenGrid weighted hospital score.

The SirenGrid side invokes the production Phase 04 planning, coverage,
repositioning, hospital, routing, and Phase 07 materiality modules. It does
not contain a benchmark-only clone of those decision rules.

Scenario state is synthetic/simulated and isolated through immutable typed
scenario inputs. Static OSM, hospital, signal, and WorldPop-derived assets
retain their original provenance labels.

## Scenario composition

The committed manifest is
`data/evaluation/phase08/scenarios.json` (`PHASE08_SCENARIO_DATASET_V1`).

The T01-T15 scenarios cover immediate activation, fusion, conflicts, blocked
roads, coverage trade-offs, hospital overload, human rejection, missing
location, resource loss, public alerts, pre-alert facts, AI fallback,
operator correction, stale data, and competing incidents.

The 21 cross-cutting scenarios cover greedy and multi-resource planning,
joint coverage, useful and rejected repositioning, stale traffic, closure,
no-path and outside-graph failures, insufficient resources, hospital
uncertainty/filtering/unavailability/reachability, material and non-material
replanning, resource outage, hospital invalidation, multi-incident outcomes,
and concurrency/idempotency.

Observed trade-offs include:

- `X04_reposition_useful`: SirenGrid selected a hypothetical move from
  `NSR-GRID-169` toward staging zone `NSR-GRID-191`, with a 598.375-second
  reposition ETA and 9,405.831 m route distance. Joint coverage improved from
  0.954634 to 0.986808 in the stored proposal facts.
- `T06_hospital_overload`: the baseline chose the nearest feasible hospital,
  while SirenGrid selected a different feasible hospital under the explicit
  simulated load fixture. Static capacity was not fabricated.
- `X11_hospital_unknown`: unknown capability remains uncertainty and does not
  become a hard incompatibility.
- `X12_hospital_incompatible`: confirmed capability filtering changes the
  feasible set; unknown capability is treated differently.
- `X15_material_eta_replan`: both engines observed the fixed closure/congestion
  fixture and the production materiality result was `MATERIAL` with a route
  edge overlap of 0.333333.
- `X16_nonmaterial_eta`: the fixed input produces
  `NO_MATERIAL_CHANGE`.
- Expected insufficient-resource cases remain visible failures in both
  engines. No resource preemption or hidden recovery was introduced.

No composite benchmark score or percentage “emergency response improvement”
is reported. Responder ETA, coverage, hospital choice, replanning, failure
handling, and runtime are separate dimensions as required by PD-058.

## Reproducibility and artifacts

The benchmark artifacts are committed under
`data/evaluation/phase08/`:

- `scenarios.json` — 36-case manifest and event/input fixtures
- `raw_scenario_results.json` — raw per-scenario, per-engine model facts
- `aggregate_results.json` — programmatically derived functional aggregates
- `performance_subset_results.json` — retained timing samples and aggregates
- `t01_t15_validation.json` — executable Master Plan validation mapping
- `expected_outcome_checks.json` — all 36 expected outcome checks
- `benchmark_metadata.json` — policy, dataset, code commit, runtime, asset
  hashes, and reality/provenance metadata

The benchmark metadata records the fixed asset hashes: OSM hospitals
`5b0439c1...02b4`, WorldPop-derived zones `d7f9a466...71d9`, routing graph
`080e9b87...d88d`, traffic signals `a83d9c3c...b145`, and the manifest
`0b088378...ed45`. Full hashes are in the metadata artifact.

The replay test removes wall-clock fields before comparing decision/model
outputs. A subsequent hardening regression verifies that traffic cache
identity includes full snapshot contents, so two snapshots with the same
identifier but different overlays cannot reuse stale travel trees.

## Measured findings

- All 36 expected baseline and SirenGrid scenario outcomes passed.
- Both engines generated 31 plans and visibly returned 5 insufficient-resource
  outcomes.
- SirenGrid retained the same median modeled incident ETA as the baseline in
  this dataset and had a slightly higher mean post-dispatch joint coverage;
  the benchmark intentionally exposes both dimensions rather than collapsing
  them into one score.
- Production repositioning and hospital ranking behavior produced observable,
  traceable differences in the designed scenarios.
- Fixed traffic replay, scenario isolation, raw outputs, and deterministic
  validation make the model findings reproducible.

## Limitations / not measured

- The 36 scenarios are synthetic/simulated fixtures, not an epidemiological or
  real Egyptian emergency-frequency sample.
- Fixed traffic fixtures do not measure current TomTom service quality. No
  live traffic claim is made.
- Wall-clock values are one Windows/Python runtime measurement and are not a
  deployment SLA.
- ASR WER/CER is `NOT_AVAILABLE` without configured provider credentials.
- Structured extraction remains `NOT_SELECTED` and default-disabled; vision
  remains default-off. No AI benchmark number was fabricated.
- The internal runner measures production decision primitives and selected
  replan materiality deterministically. It does not replace the existing
  database-backed Phase 07 operational approval flow; that flow remains
  covered by its own regression suite.
- No global optimizer, composite utility score, real hospital integration,
  real signal control, frontend, or Phase 09 behavior was added.

Claims not justified by this artifact include universal emergency-response
improvement, official SLA compliance, real-world incident-distribution
performance, live hospital capacity, or real government integration success.
